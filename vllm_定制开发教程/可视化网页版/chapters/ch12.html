第 12 章 · 异构硬件部署
CHAPTER 12

异构硬件部署指南：NVIDIA / AMD / Intel / CPU / 昇腾

🔖 vLLM v0.31.0🔧 动手实验
本章目标：讲清 vLLM 的硬件抽象层——同一套调度/KV 管理代码，如何在完全不同的芯片上跑起来；以及每种硬件的真实安装部署步骤。（平台文件对照 vLLM v0.31.0：vllm/platforms/ 下有 interface.py、cuda.py、rocm.py、cpu.py、xpu.py、tpu.py、zen_cpu.py）

12.0核心设计：一套引擎，多种芯片

回忆第 03 章架构图。vLLM 的聪明之处在于：调度器、KV Cache 管理、API 层、采样器都是纯 Python + 平台无关逻辑，真正与芯片绑定的只有三处：

平台相关部位内容对应抽象
注意力/矩阵内核FlashAttention、GEMM 等数学实现attention backends（第 11 章 MLA 一族就是范例）
通信NCCL / RCCL / oneCCLvllm/distributed/device_communicators/（cuda/xpu/cpu 各有 communicator）
Worker 执行显存摸底、CUDA Graph、kernel 启动vllm/platforms/interface.py 的 Platform 抽象类

vllm/platforms/__init__.py 提供 current_platform 单例：启动时自动检测硬件并实例化对应的 Platform 子类，之后引擎所有"这是 N 卡还是 A 卡"的分叉都问它。

内置平台 5 种：CUDA（NVIDIA）、ROCm（AMD）、CPU、XPU（Intel）、TPU（Google）。不在内置列表的芯片怎么办？→ 插件机制（下一节，也是本章最重要的一页）。

Platform 平台抽象与硬件适配链路上层平台无关，芯片绑定集中在三处 · 对应 12.0 节

12.1硬件插件机制：以昇腾 vllm-ascend 为范例

华为昇腾 NPU 不在 vLLM 内置平台里，但它是 vLLM 官方背书的硬件插件参考实现（vLLM 团队 2025 年 5 月官方博客《Introducing vLLM Hardware Plugin, Best Practice from Ascend NPU》）。它的接入原理，正是第 13 章插件体系的"平台插件组"：

text · vllm-ascend 接入原理示意
vllm-ascend 包的 pyproject 里注册了 vllm.platform_plugins 入口点
        │
        ▼
vLLM 初始化 current_platform 时发现该插件 → 加载 AscendPlatform
        │
        ▼
AscendPlatform 替换/扩展默认行为:
    - device 类型、显存查询方式(npn-smi 体系)
    - Worker / ModelRunner 换成 NPU 版实现
    - 注意力内核、通信库(CCL)按昇腾算子库适配
        │
        ▼
对用户而言: 引擎层一切照旧 —— vllm serve 命令参数几乎不变

这就是"解耦"的商业价值：芯片厂商不必往 vLLM 主仓塞几千行硬件代码，vLLM 核心也不被单一硬件绑架；版本对齐通过"vllm-ascend 版本线跟随上游 vLLM 版本线"解决（例如 vllm-ascend v0.30.x 对齐上游 vLLM v0.30，2026-10 发布的 v0.30.0rc1 即与 vLLM v0.30.0 通过 main2main 流程对齐）。

12.2分硬件部署实操

① NVIDIA CUDA（基线，本教程演示机）

bash
pip install -U vllm          # 轮子自带 CUDA 运行时, 只需驱动够新
vllm serve Qwen/Qwen2.5-0.5B-Instruct

要点：TP 优先 NVLink 机器（第 07 章）；日志 # GPU blocks 是容量规划第一指标。

② AMD ROCm

bash
# 方式一: 官方 Docker(最省心)
docker run --ipc=host --shm-size 16G --device /dev/kfd --device /dev/dri \
  -p 8000:8000 rocm/vllm:latest \
  vllm serve Qwen/Qwen2.5-7B-Instruct

# 方式二: pip (ROCm 版 torch 轮子)
python3 -m pip install vllm --extra-index-url https://download.pytorch.org/whl/rocm6.4

要点：

  • ROCm 版支持的模型/量化集合略窄于 CUDA（MLA 有 aiter_triton_mla.py 专供 AMD）；
  • 通信库换成了 RCCL（NCCL 的 AMD 等价物）——对你是透明的；
  • 模型兼容性以官方 "AMD 安装与支持矩阵" 文档为准。

③ Intel XPU（含 Arc / Gaudi 路线）

bash
# 平台抽象文件: vllm/platforms/xpu.py
# 安装遵循 Intel 官方仓库(vllm fandom 文档 / intel-extension-for-pytorch 指南)
pip install vllm --extra-index-url https://download.pytorch.org/whl/xpu
vllm serve Qwen/Qwen2.5-1.5B-Instruct --device xpu

要点：XPU 通信走 oneCCL（device_communicators/xpu_communicator.py）；生态成熟度弱于 CUDA，新特性跟进通常滞后数个版本，生产选型前必跑官方支持矩阵。

④ 纯 CPU（本教程 8% 场景的救星）

bash
pip install vllm --extra-index-url https://download.pytorch.org/whl/cpu
# 平台抽象: vllm/platforms/cpu.py(+ zen_cpu.py 针对 AMD Zen 优化)
vllm serve Qwen/Qwen2.5-0.5B-Instruct --max-model-len 1024

要点：0.5~1.5B 模型 + 短上下文可实用；学习 API/流程/插件开发完全够用；MLA 都有 CPU 实现（amx_mla.py，Intel AMX 指令加速）。

⑤ 华为昇腾 NPU（国产主力）

bash
# 1. 确认驱动(推荐 HDK 25.5.0+)
npu-smi info

# 2. 官方容器(推荐, 免去版本对齐烦恼) —— vllm-ascend 发布线对齐上游 vLLM
docker run --rm --name vllm-ascend --net=host --shm-size=1g \
  --device /dev/davinci0 \
  quay.io/ascend/vllm-ascend:v0.13.0rc3 \
  vllm serve deepseek-ai/DeepSeek-R1-Distill-Qwen-7B

# 3. 或 pip 双装(注意: vllm 与 vllm-ascend 版本必须成对!)
pip install vllm==0.9.2 vllm-ascend==0.9.2rc1

要点（截至 2026-10 的 vllm-ascend v0.30.0rc1）：

  • 版本纪律是第一铁律：vllm 与 vllm-ascend 版本线必须配对，跨线混装必出玄学错误；
  • 旗舰适配以"模型×硬件组合"白名单发布（该版本聚焦 DeepSeek V4.1、GLM-5.3、Qwen3.8 等旗舰模型），白名单外的组合"能跑"不代表"承诺支持"；
  • 深度优化方向：大规模专家并行、PD 分离部署、KV Cache Pool、TurboQuant 低比特 KV——都是第 04~09 章原理在另一种芯片上的再现。

⑥ Google TPU（了解）

vllm/platforms/tpu.py；需 GCP 环境 + 专用轮子，JAX/Pallas 内核路线，属于特定云上场景，用到时查官方 TPU 文档即可。

12.3跨硬件通用排错心法

症状排查方向
启动就崩、怀疑平台没对python -c "from vllm.platforms import current_platform; print(current_platform)" 看检测结果
报错提到某 kernel 不存在该硬件未实现此内核 → 查平台支持矩阵/换模型/换量化
性能远低于官方数据确认是否在官方白名单"模型×硬件×并行"组合内
多卡起不来通信库问题：NCCL/RCCL/CCL 环境变量与版本

12.4动手实验

✅ 实验 12-1（必做）：平台自省

bash
python3 -c "
from vllm.platforms import current_platform as p
print('平台:', p)                      # 本机应显示 CudaPlatform
print('设备名:', p.get_device_name())
"

✅ 实验 12-2（推荐）：同一命令在两种硬件跑通。用 CPU 版 vLLM（单独 venv）跑 first_run.py，对比 CUDA 版的吞吐差距（通常 10~50 倍）——体会"引擎逻辑相同、内核不同、性能天差地别"，这正是本章的题眼。

🔬 实验 12-3（选做）：读 vllm/platforms/interface.py 的 Platform 抽象类，列出至少 5 个"平台必须回答的问题"（如 is_cuda()、显存查询、graph 模式支持…），再打开 cuda.py 看答案——硬件插件要做的就是把这些问题全部答一遍。

CHAPTER 14

硬件与模型适配的代码级细节（深入 Platform 与内核选择链路）

🔖 vLLM v0.31.0🔬 硬核实验
本章目标：从"会用"到"能改"。把第 12 章的平台抽象和第 10/11 章的模型适配拆到方法签名级——所有代码片段都来自 vLLM v0.31.0 真实源码（本章撰写时已逐一核对）。学完你能回答："vLLM 在哪一行决定用哪个内核？我要加一种硬件/换一个内核，代码改在哪？"

14.1Platform 抽象类：硬件要回答的"问卷"

源码：vllm/platforms/interface.py（约 1300 行，本章建议精读的文件）。所有平台（内置或插件）都要实现这张"问卷"。按用途分组的关键方法（真实签名摘录）：

vllm/platforms/interface.py（真实签名摘录）
class Platform:
    # ── ① 身份识别 ──
    def is_cuda(self) -> bool ...        # is_rocm/is_tpu/is_xpu/is_cpu/is_zen_cpu
    def is_cuda_alike(self) -> bool      # CUDA 与 ROCm 通吃的判断(内核兼容时用它)
    def is_out_of_tree(self) -> bool     # 是否来自硬件插件(第12章昇腾=True)
    def get_device_capability(self) -> DeviceCapability    # 算力代际(如 (8,9)=Hopper)

    # ── ② 能力声明 ──
    @property
    def supported_dtypes(self) -> list[torch.dtype]        # 该芯片支持哪些精度
    def is_sleep_mode_available(self) -> bool              # 权重休眠(省显存切换)
    def is_cumem_allocator_available(self) -> bool         # CUDA 内存池特性

    # ── ③ 内核与编译 ──
    @classmethod
    def get_attn_backend_cls(cls, selected_backend, head_size, dtype, ...) -> str
        # ★★ 决定注意力内核的一句话! 返回类名字符串, 如
        #    "vllm.v1.attention.backends.flash_attn.FlashAttentionBackend"
    @classmethod
    def get_supported_vit_attn_backends(cls) -> list[...]   # 视觉塔的内核候选
    @classmethod
    def import_kernels(cls) -> None                         # 按需导入内核包
    @classmethod
    def register_triton_kernel_overrides(cls) -> None       # 注册 triton 覆盖
    @classmethod
    def get_compile_backend(cls) -> str                     # torch.compile 后端
    @classmethod
    def import_ir_kernels(cls) -> None                      # IR 层内核(见14.4)

    # ── ④ 设备拓扑 ──
    @classmethod
    def device_id_to_physical_device_id(cls, device_id)     # 逻辑卡号→物理卡号
    @classmethod
    def logical_device_id_to_visible_device_id(cls, ...)    # CUDA_VISIBLE_DEVICES 体系

读法：这张问卷的每一题，都是引擎某处 current_platform.xxx() 的调用点。例如调度/采样代码判断精度能力时问 supported_dtypes；ModelRunner 建注意力层时问 get_attn_backend_cls；多卡初始化时问 device_id 三件套。

14.2一次"内核选择"的完整代码链路

以"Qwen3-0.6B 在 RTX 4060 上为什么用 FlashAttention 后端"为例，追踪代码：

内核选择链路（示意）
ModelRunner 构建注意力层
   │  调用 current_platform.get_attn_backend_cls(...)
   ▼
vllm/platforms/cuda.py → 先看用户显式指定的 --attention-backend / env
   │  没指定 → 按 DeviceCapability + 库可用性(flash_attn/flashinfer/triton)仲裁
   ▼
返回 "vllm.v1.attention.backends.flash_attn.FlashAttentionBackend"
   │  (字符串→import→实例化, 每层 Attention 模块持有该 backend)
   ▼
前向时: FlashAttentionMetadata.build(...) 把调度器给的 block_table(第04章)
        翻译成内核参数 → 调 paged FlashAttention CUDA/Triton 内核
Platform 问卷与内核选择链路点击组件，看它在这条适配链路里的职责（对应 14.1 / 14.2）

换平台时的分叉点：rocm.py 的同名方法会返回 AITER/Triton 系内核；昇腾插件返回自研内核——引擎其余代码一行不改，这就是第 12 章"三个绑定部位"中注意力内核的实际实现机制。

🔍 动手验证链路（无需改代码）：
python3 -c "from vllm.platforms import current_platform as p; print(p.get_attn_backend_cls(...))"
或启动时看日志行 Using ... FlashAttentionBackend——它就是这条链路的终点输出。

14.3跨平台条件导入：vLLM 的教科书模式

硬件插件代码最常见的坑：import tilelang/import aiter 这类硬件专属库在错误的平台上 import 直接崩。vLLM 的标准解法（真实源码摘自 vllm/tilelang_utils/__init__.py）：

vllm/tilelang_utils/__init__.py
from vllm.platforms import current_platform
from vllm.utils.import_utils import has_tilelang

if TYPE_CHECKING or current_platform.is_cuda():        # ① 只有 CUDA 平台才立即导入
    if not has_tilelang():
        raise ImportError("tilelang is required ... `pip install tilelang`")
    import tilelang
    import tilelang.language as T
else:
    tilelang = None                                    # ② 其他平台: 置 None 占位
    T = None

def _ensure_tilelang_imported() -> None:              # ③ ROCm 等平台延迟到"首次调用"
    global T, tilelang
    if tilelang is not None:
        return
    import tilelang as tilelang_module
    import tilelang.language as tilelang_language
    tilelang, T = tilelang_module, tilelang_language   # ④ 绑回模块全局

四条军规（写硬件相关代码时背下来）：

  1. 模块级 import 必须带平台门卫（TYPE_CHECKING or current_platform.is_cuda()——TYPE_CHECKING 保证类型检查器不报错）；
  2. 不能立即导入的平台置 None，并用 _ensure_xxx_imported() 提供延迟绑定；
  3. 缺库要给安装指引（raise 里带 pip 命令）；
  4. 所有内核入口先 ensure 再用。

顺带一提：仓库里的测试 tests/kernels/scripts/check_no_tilelang_hijack.py 守护的是另一件事——TileLang 导入时会修改一些全局环境（"hijack"），vLLM 用 CI 测试确保 import 时机受控。集成第三方 DSL 库时，警惕它的 import 副作用，这是本节更深一层的工程教训。

14.4模型适配的代码级 Checklist（从 config 到 kernel）

把第 10/11 章的"四步法"落到文件级操作表。假设新增架构 MyModelForCausalLM：

#改哪里具体内容参考文件
1模型实现类 + forward() + load_weights()（权重名映射!）抄 models/qwen2.py
2注册表_MODELS["MyModelForCausalLM"] = ("my_model", "MyModel")models/registry.py
3任务声明generate/pool 支持声明vllm/tasks.py
4注意力用统一 Attention 层 → 自动获得当前平台的 backendlayers/attention

6量化config quantization_config → 对应 quant 方案自动挂钩layers/quantization/

其中 #4 是"免费午餐"的关键：只要模型用的是 vLLM 统一 Attention 层，block_table 传递、backend 选择、TP 切分全部自动成立——这就是第 11 章"三家模型 90% 同构"能成立的技术根基。

14.5优化定位方法论：先量化，再动手

写优化代码前，必须先回答"慢在哪"。vLLM 生态的定位工具链（由浅入深）：

层级工具看什么
服务级/metrics + vllm bench serve（第 09 章）TTFT/TPOT/吞吐, 定位阶段
进程级VLLM_LOGGING_LEVEL=DEBUG、torch.profiler（vLLM 内置 profiler 开关）每个算子的 CPU/GPU 时间
kernel 级nsys profile / ncu（Nsight Compute）kernel 耗时榜、带宽/算力利用率、占用率
静态torch.cuda.memory_summary()显存碎片/峰值

判定优化的两条铁律：

  1. 先分类：kernel 慢是因为算力满（compute-bound）还是带宽满（memory-bound）？——ncu 的 SOL（Speed Of Light）表直接给答案。RMSNorm 类=带宽型（去拼合并访存/向量化），GEMM 类=算力型（去拼 tile/pipeline/TensorCore）；
  2. 对比基准必须同精度同条件：fp16 vs fp32 的"提速"多半是精度作弊。

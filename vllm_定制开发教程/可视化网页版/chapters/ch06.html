CHAPTER 06

一次请求的完整旅程（源码走读）

🔖 vLLM v0.31.0🔧 动手实验
本章目标：跟着一个 HTTP 请求钻进 vLLM 源码，从 FastAPI 路由一路走到 CUDA 内核再回来。学完你将获得"源码导航能力"——以后任何 vLLM 问题，都知道去哪个文件找答案。所有路径基于 vLLM v0.31.0。

6.0走读前的准备

bash
# 找到 vLLM 源码位置，用支持"跳转定义"的编辑器（VSCode + Pylance）打开
python -c "import vllm, os; print(os.path.dirname(vllm.__file__))"

走读纪律（小白最容易犯的错）：

  1. 跟着请求走，不顺着文件读——只看请求经过的代码；
  2. 先看函数签名和 docstring，再决定要不要进函数体；
  3. 每个函数只回答一个问题："它为这个请求做了什么"。

6.2第一站：API 层（进程 1）

文件：vllm/entrypoints/openai/api_server.py

  • vLLM 用 FastAPI 定义了完整的 OpenAI 兼容路由：/v1/chat/completions、/v1/completions、/v1/models、/v1/embeddings 等；
  • 收到 chat 请求后：读取 model → 应用 chat template（把 messages 数组渲染成模型的 prompt 字符串）→ 构造 SamplingParams；
  • 然后把任务交给本文件的灵魂——AsyncLLM。

文件：vllm/v1/engine/async_llm.py → 类 AsyncLLM

vllm/v1/engine/async_llm.py
AsyncLLM.from_engine_args(engine_args)   # 启动时: 拉起 EngineCoreProc 子进程
async def generate(request_id, prompt, params):
    await self.output_handler ...        # 注册输出流
    self.engine_core.add_request(...)    # ZMQ 发给引擎子进程
    async for output in stream: ...      # 收一步吐一步

要点：

  • add_request 只是"挂号"：它把请求放进队列就返回，绝不阻塞——这就是它能扛高并发的第一步；
  • AsyncLLM 与 EngineCoreProc 之间是 ZMQ 双向通道：去程（请求）、回程（每步的 token 增量）。

6.3第二站：引擎主循环（进程 2）

文件：vllm/v1/engine/core.py → 类 EngineCore（常驻循环体）

vllm/v1/engine/core.py
# EngineCore 的主循环（简化示意，真实代码即 step 的重复）
while True:
    out = self.step()   # 一个"节拍"
    # step 内部三连:
    #   1. scheduled = self.scheduler.schedule()          # 第05章已精讲
    #   2. output = self.model_executor.execute_model(scheduled)  # 下一站
    #   3. 把每请求的新 token 通过 ZMQ 发回 AsyncLLM

如果配置了多卡（TP/PP），model_executor 会广播这批任务给每张卡的 Worker（第 07 章）。

6.4第三站：模型执行层

文件：vllm/v1/worker/gpu_model_runner.py → 类 GPUModelRunner

execute_model(scheduler_output) 是 GPU 侧的总入口，做四件事：

  1. 准备输入张量：把这一批所有请求的 token ids 拼接、按 block_table 定位每条序列的 KV 位置（其中就包括把页表传给注意力内核）；
  2. 选择执行路径：decode 批命中 CUDA Graph 直接重放（省掉上千次 kernel 启动开销）；prefill/混批走普通路径（V1 的 piecewise CUDA Graph 会分段处理）；
  3. 调用模型 forward：进入 vllm/model_executor/models/ 下对应模型（如 qwen2.py 的 Qwen2ForCausalLM），逐层执行；
  4. 注意力内核：每层注意力调用 vllm/v1/attention/backends/flash_attn.py（FlashAttention 后端）——PagedAttention 在 V1 中以"页表感知的 FlashAttention"形式存在，它按 block_table 逐块读取 KV 完成注意力计算（第 04 章机制在这里落地）；
  5. 采样：logits → vllm/v1/sample/ 采样器（temperature/top_p/penalties...）→ 本步的 token id。

6.5第四站：结果回传（回到进程 1）

文件：vllm/v1/engine/output_processor.py + detokenizer.py

  • 每个请求有独立状态机（RequestState）：WAITING → RUNNING → FINISHED/ABORTED；
  • 收到 token id → 增量反分词（注意坑：UTF-8 汉字可能被拆在两个 token 里，detokenizer 要缓存不完整字节，直到凑齐才输出）；
  • 组装 RequestOutput（含 delta 文本、完成原因 stop/length、token 计数）推回 AsyncLLM 的输出队列；
  • API 层把 delta 包成 SSE data: {...} 帧发出——你看到的"打字机"由此而来。

6.6全程飞行记录仪：给关键路径插桩

纸上得来终觉浅。下面这个 monkeypatch 脚本不改源码文件，就能在运行时打印关键事件：

lab/instrument.py
# lab/instrument.py —— 飞行记录仪（真机运行）
import vllm.v1.engine.core as core_mod
from vllm import LLM, SamplingParams

orig_step = core_mod.EngineCore.step

def my_step(self):
    sched = self.scheduler
    print(f"[step] running={len(sched.running)} waiting={len(sched.waiting)}")
    out = orig_step(self)
    return out

core_mod.EngineCore.step = my_step   # 猴子补丁: 包一层

llm = LLM(model="Qwen/Qwen2.5-0.5B-Instruct",
          max_model_len=512, gpu_memory_utilization=0.85)
llm.generate([f"问题{i}：介绍一下春天。" for i in range(6)],
             SamplingParams(max_tokens=32, ignore_eos=True))
bash
python lab/instrument.py
# 观察输出: 开始时 waiting=6 → 逐步全部转入 running → 结束前逐个退出

这个技巧叫 monkeypatch 插桩，是二次开发前最安全的观察手段——不改一行源码文件，先看清内部行为。第 10 章定制开发会大量用到。

6.7源码导航手册（遇到问题去哪查）

现象/问题先看哪里
某参数不生效/含义不明vllm/engine/arg_utils.py（全部参数的注释与默认值）
请求排队久、抢占频繁vllm/v1/core/sched/scheduler.py
KV 显存相关vllm/v1/core/kv_cache_manager.py、kv_cache_utils.py
输出乱码/截断vllm/v1/engine/detokenizer.py
吞吐上不去gpu_model_runner.py（CUDA Graph 路径）+ 第 09 章
新模型支持vllm/model_executor/models/registry.py（第 10 章）
API 报错行为vllm/entrypoints/openai/api_server.py

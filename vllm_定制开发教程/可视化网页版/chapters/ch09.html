CHAPTER 09

服务化部署与性能调优

🔖 vLLM v0.31.0🔧 动手实验
本章目标：把前 8 章的知识转化为生产力——会压测、会读指标、会按业务调参、会排错。这一章是"面试/工作"高频实战章节。

9.1服务化部署清单（生产 Checklist）

bash · 生产启动命令
vllm serve <模型> \
  --host 0.0.0.0 --port 8000 \
  --max-model-len 8192 \               # 按业务最长上下文设, 不要无脑拉满(吃 KV 座位)
  --gpu-memory-utilization 0.90 \      # 独占机器可 0.9+; 与其他进程混部要下调
  --max-num-seqs 256 \                 # 并发上限, 按业务峰值调
  --enable-prefix-caching \            # 有共同前缀就开(V1 默认开)
  --disable-log-requests               # 生产关闭请求日志(隐私+性能)

其他生产要点：

  • 健康检查：/health 端点接负载均衡探活；
  • 优雅退出：SIGTERM 会先清空队列；K8s 部署时配好 terminationGracePeriodSeconds；
  • 模型放本地盘：避免运行中从对象存储拉模型（启动风暴）；
  • Docker：官方镜像 vllm/vllm-openai:v0.31.0，挂载 HF 缓存目录避免重复下载。

9.2四个必懂指标（背下来）

指标全称含义用户感知
TTFTTime To First Token从发请求到第一个 token 的时间"卡了多久开始打字"
TPOTTime Per Output Token平均每个 token 的生成耗时"打字快不快"
ITLInter-Token Latency相邻两个 token 的间隔（逐个测）"打字稳不稳"(顿挫感)
Throughput—系统级 tokens/s总容量/成本

关键洞察（把前几章串起来）：

  • TTFT 主要由 prefill 排队 + prefill 耗时 决定 → 治理手段：调度预算、chunked prefill、前缀缓存；
  • TPOT/ITL 主要由 decode 步长 + 每步批大小 决定 → 治理手段：max_num_seqs 适配、CUDA Graph、投机解码；
  • TTFT 和吞吐此消彼长：接太多新请求（大 prefill）会拖慢在跑请求的 ITL。调度器的一切预算设计都在平衡这两者。

9.3压测：vLLM 自带工具

bash
# 服务端
vllm serve Qwen/Qwen2.5-0.5B-Instruct --max-model-len 2048 &

# 客户端压测(内置 benchmark 工具, 模拟随机长短的请求)
vllm bench serve \
  --backend vllm \
  --model Qwen/Qwen2.5-0.5B-Instruct \
  --num-prompts 200 \
  --request-rate 10        # 每秒 10 个请求, 泊松到达

# 输出会给出: 成功数、吞吐、TTFT 均值/P99、TPOT/P99

标准压测流程（面试可直接说）：

  1. 固定 request-rate 从低到高扫（1/5/10/20/50）；
  2. 每档记录 TTFT-P99、TPOT-P99、吞吐；
  3. 找到 TTFT-P99 突破 SLO 的拐点 = 该配置的最大服务容量；
  4. 改一个参数（如 max-num-seqs）重复，得到最优配置。

9.4调优决策树（实战心法）

示意 · 调优决策树
吞吐不达标?
├─ KV blocks 太少(日志里看) → 减 max-model-len / 量化 KV(fp8) / 量化权重
├─ running 一直 < max-num-seqs → 并发不足, 加大压测速率; 客户端是瓶颈?
├─ 单步太慢(大批) → 减 max-num-seqs; 开投机解码
└─ GPU 利用率波动大 → 开 chunked prefill 平滑; 检查是不是 CPU/分词器瓶颈

TTFT 太高?
├─ prefill 排队 → 加大 max-num-batched-tokens; 长请求切分
├─ 有共同前缀但没命中 → 检查 prompt 模板是否逐字节一致(第08章)
└─ 大 prompt 一次塞入 → 开 chunked prefill

ITL 顿挫?
├─ 长 prefill 插队 → 确认 chunked prefill 生效
├─ 抢占频繁(日志 grep Preempted) → 减 max-num-seqs 或加显存
└─ 采样参数复杂(logit_bias 等) → 精简

9.5排错手册（对照日志）

日志/报错根因处置
CUDA out of memory at startuputilization 太高 / max-model-len 太大下调 utilization；减 max-model-len；第 08 章量化
Preempted request ... (RECOMPUTE) 刷屏KV 块耗尽，抢占风暴降并发/降 max-model-len/量化 KV
# GPU blocks 远小于预期有别的进程占显存 / utilization 低nvidia-smi 查占用；独占机器提 utilization
输出中文出现"半个字"客户端自行拼接 delta 时未处理增量反分词使用返回的 delta 全量顺序拼接，别跳帧
TTFT 突然飙高前缀缓存失效(模板改动) / 有超长请求检查 prompt 模板；加 chunked prefill
ValueError: The model's max seq len is larger than ...KV 座位装不下 max-model-len减 max-model-len 或量化

9.6监控与可观测性

  • /metrics 暴露 Prometheus 指标（请求排队数、运行数、token 计数、缓存命中、各阶段延迟直方图）；
  • 最小监控三件套：num_requests_running、num_requests_waiting、TTFT 直方图 P99；
  • Grafana 有社区现成 dashboard，导 vLLM 指标即可。

9.7动手实验

🚀 实验 9-1（必做）：完成一次完整压测报告

bash
# 1. 起服务(记录: # GPU blocks, Maximum concurrency)
# 2. 三档速率压测, 抄录关键数字:
vllm bench serve --backend vllm --model Qwen/Qwen2.5-0.5B-Instruct \
  --num-prompts 100 --request-rate 5
vllm bench serve --backend vllm --model Qwen/Qwen2.5-0.5B-Instruct \
  --num-prompts 100 --request-rate 20
vllm bench serve --backend vllm --model Qwen/Qwen2.5-0.5B-Instruct \
  --num-prompts 100 --request-rate 50
# 3. 把 TTFT/TPOT/吞吐 填入表格, 找出你这套配置的容量拐点

🚀 实验 9-2：单参数敏感性

只改 --max-num-seqs（如 16 / 64 / 256）重复实验 9-1，画出"吞吐-延迟"曲线，验证 5.4 参数表的结论：并发上限是吞吐与单请求延迟之间的旋钮。

🔬 实验 9-3：复现一次抢占风暴

--max-model-len 拉大 + 小 utilization 启动，并发发送多个接近 max 长度的请求，grep Preempted 观察风暴；然后按 9.4 决策树逐项治理，直到日志安静。（这个过程就是生产排错的真实缩影。）

CHAPTER 03

vLLM 整体架构鸟瞰

🔖 vLLM v0.31.0🔧 动手实验
本章目标：建立 vLLM 的"地图"。学完你能说出：一个请求从进来到出去，经过哪几个进程、哪几个模块；看启动日志不再懵；看到源码目录知道往哪儿翻。（所有文件路径均对照 vLLM v0.31.0 真实源码树核对）

3.1一张总图：四个世界

把 vLLM 想象成一家"高级餐厅"：

示意 · 四个世界（分层总图）
┌────────────────────────────────────────────────────────────────────────┐
│ 世界一：前台 API 层（进程1，跑 FastAPI）                                  │
│   接待客人、翻译菜单、收发消息 —— 但不做菜                                 │
│   vllm/entrypoints/openai/api_server.py（FastAPI 路由）                  │
├────────────────────────────────────────────────────────────────────────┤
│ 世界二：引擎调度层（进程2，EngineCore）                                   │
│   大堂经理：决定谁上桌、几个人一桌、桌子不够了让谁腾                       │
│   vllm/v1/engine/core.py + vllm/v1/core/sched/scheduler.py              │
├────────────────────────────────────────────────────────────────────────┤
│ 世界三：模型执行层（进程2内 或 每张GPU一个进程）                           │
│   后厨：真正拿锅炒菜（跑模型前向计算）                                    │
│   vllm/v1/worker/gpu_worker.py + gpu_model_runner.py                    │
├────────────────────────────────────────────────────────────────────────┤
│ 世界四：算子/内核层（CUDA/Triton 库）                                     │
│   菜刀案板：FlashAttention、GEMM 内核等最底层的数学计算                    │
│   vllm/v1/attention/backends/ + vllm/model_executor/layers/             │
└────────────────────────────────────────────────────────────────────────┘
vLLM 架构分层图点击任意组件，查看职责与源码位置（对应 3.1 节）

为什么前台和厨房分成两个进程？ 三个原因（V1 架构最重要的设计决策）：

  1. GIL 隔离：Python 的全局锁会拖累高频调度循环。引擎子进程（EngineCoreProc）里是纯 Python 高速循环，与处理 HTTP 的 asyncio 事件循环互不干扰；
  2. 故障隔离：内核崩溃（CUDA error）不会拖垮 API 服务，还能被监控重启；
  3. 可扩展：多卡/多机时，EngineCore 可以指挥多个 Worker 进程，前台完全无感。

进程间通过 ZMQ 消息队列（+ 共享内存传大块 tensor）通信，这是 V1 架构"AsyncLLM ↔ EngineCore"的标准协议。

3.2两种入口，一套核心

入口文件用途去向
LLM(...) 离线vllm/entrypoints/llm.py脚本实验、批量处理同步包装 EngineCore
vllm serve 在线vllm/entrypoints/openai/api_server.py + vllm/v1/engine/async_llm.py（类 AsyncLLM）生产 API 服务HTTP → AsyncLLM → EngineCore

记住这张关系图（本课程的主旋律）：

3.4一次启动，vLLM 做了什么？

LLM(...) 构造函数（或 serve 启动）的内部时间线——建议对照启动日志读一遍：

示意 · 启动时间线
[1] 解析配置      EngineArgs → 各 Config 对象（arg_utils.py 里 500+ 个参数）
[2] 创建引擎进程   EngineCoreProc（子进程），加载 tokenizer
[3] 加载模型权重   dtype/量化判断 → 从 HF 下载/读取 safetensors → 装载到 GPU
[4] 显存摸底      Worker.profile_run()：用假数据跑一遍前向，测出
                  "模型+激活"实际吃掉多少显存
[5] 分配 KV Cache 可用显存 = 总显存 × gpu_memory_utilization − 摸底结果
                  按 block_size(16 token) 切块 → 得到 "# GPU blocks: N"
                  一次性预分配整块 KV Cache 张量（之后运行期不再向 PyTorch 要显存!）
[6] CUDA Graph    把 decode 阶段的前向录制为 CUDA Graph，消除逐层 kernel 启动开销
[7] 就绪          打印 "Maximum concurrency"，开始服务

步骤 [4][5] 是 vLLM 显存哲学的精髓：先测量再分配，把"剩余显存"全部变成 KV Cache 座位，运行期完全静态化——避免了 PyTorch 缓存分配器的抖动，这是它能塞下更多请求的物理基础。

3.5动手实验

✅ 实验 3-1（必做）：带 DEBUG 日志启动，亲眼看到上述步骤：

bash
VLLM_LOGGING_LEVEL=INFO vllm serve Qwen/Qwen2.5-0.5B-Instruct --max-model-len 1024 2>&1 | tee serve.log

对照 3.4 的时间线，在 serve.log 里找到每个阶段对应的日志行，做上标注。

✅ 实验 3-2（必做）：服务启动后，问它要配置快照：

bash
curl http://localhost:8000/v1/chat/completions -H "Content-Type: application/json" \
  -d '{"model":"Qwen/Qwen2.5-0.5B-Instruct","messages":[{"role":"user","content":"hi"}]}'
curl http://localhost:8000/metrics | grep -E "num_requests_(running|waiting)"   # Prometheus 指标

压测时反复请求 /metrics，观察 running（正在跑的请求数）和 waiting（排队数）的消长——这就是调度器（第 05 章）在实时工作。

✅ 实验 3-3（选做）：在自己环境里翻源码。装完 vLLM 后：

bash
python -c "import vllm, os; print(os.path.dirname(vllm.__file__))"
# 用编辑器打开该目录，对照 3.3 的地图逐个打开标注 ★ 的文件
# 只看：文件开头 docstring、class 定义、主要 public 方法签名。不要陷进细节！

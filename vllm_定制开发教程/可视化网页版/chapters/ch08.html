第 08 章 · 高级特性
CHAPTER 08

高级特性：Chunked Prefill、投机解码、量化、结构化输出、LoRA

🔖 vLLM v0.31.0🔧 动手实验
本章目标：掌握 vLLM 五大"加速/增强开关"的原理与用法。每个特性都遵循：问题 → 原理 → 用法 → 实验观察。

8.1Chunked Prefill（V1 默认开启）

问题：一个 20000 token 的 prompt 若一步 prefill，会霸占 GPU 数百毫秒，同一时间所有 decode 请求的流式输出全部卡顿（第 05 章已预告）。

原理：调度器把超长 prompt 按 --max-num-batched-tokens 预算切片，多步内分批算完。切片期间还能与其他请求的 decode 混批，GPU 利用率更平滑。

用法（默认开，一般不用动）：

bash
vllm serve Qwen/Qwen2.5-0.5B-Instruct --max-num-partial-prefills 2   # 允许 2 个长请求同时切片

观察：用长 prompt + 流式请求，对比开启/关闭时打字机是否顿挫。

8.2前缀缓存进阶（第 04 章的延伸）

V1 默认 --enable-prefix-caching。三个进阶用法：

bash
# ① 多轮对话场景天然受益: 每轮对话的前缀 = 上一轮的完整上下文
# ② 配合 --num-gpu-blocks-override 手动固定块数做容量规划
# ③ 查命中率: /metrics 里的 cache 相关指标, 或日志 "Prefix caching"

踩坑提示：请求间前缀缓存命中要求 token 完全一致——温度、采样参数不同不影响，但 prompt 开头哪怕差一个空格都会 miss。模板化的 prompt（如 RAG 固定文档段）要放在开头。

8.3投机解码（Speculative Decoding）：用"猜"换速度

问题：decode 每步只出 1 个 token，却要搬一次全部权重（访存瓶颈），小算量大搬运，GPU 计算单元大量闲置。

原理：请一个便宜的"草稿模型"（或 n-gram 表）先连猜 k 个 token，再让大模型一步并行验证这 k 个——被接受的直接采纳，猜错处回退。一次前向搬运权重，产出多个 token，数学上输出分布与不用它时完全一致（这是关键，纯赚不亏）。

示意 · 草稿-验证一轮
草稿(小模型/ngram): 猜 "天/空/很/蓝"     (极快)
目标(大模型):       一次前向同时验证 4 个  (成本≈原本1步)
结果: 接受 "天空很" 拒绝 "蓝" → 本步产出 3 个 token, 3倍速!

vLLM v0.31 支持多种草稿方式（vllm/v1/spec_decode/）：n-gram（零成本、适合翻译/代码等重复模式多的任务）、小模型草稿（EAGLE 系列、Medusa 等）。

用法：

bash
# n-gram 投机: 最容易上手
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --speculative-config '{"method": "ngram", "num_speculative_tokens": 5}'

观察：压测对比开启前后吞吐；日志会报告接受率（acceptance rate）——任务可预测性越高（代码补全/固定格式）收益越大，创意写作收益低甚至负收益。

投机解码：草稿-验证博弈动画演示"连猜 k 个 → 一步验证 → 采纳/回退"

8.4量化：显存不够的第一反应

原理：把 FP16 权重压到更低比特（FP8/INT8/INT4），显存和带宽都省 2~4 倍。KV Cache 也能量化（--kv-cache-dtype fp8），直接让"座位"翻倍。

方案特点用法
FP8近乎无损、NVIDIA Hopper/Ada+ 硬件原生支持，首选--quantization fp8（或直接加载官方 FP8 模型）
AWQ4bit，精度好，需预量化模型直接加载 *-AWQ 命名的模型
GPTQ4bit，生态成熟直接加载 *-GPTQ 模型
bitsandbytes8/4bit 在线量化（对任意 HF 模型即拿即用，速度一般）--quantization bitsandbytes
量化档位对比 · 每权重比特数数值取自 8.4 正文：FP16 → FP8/INT8 → INT4

实操（8GB 卡跑 7B 的正确姿势——不用并行，不用租卡）：

bash
vllm serve Qwen/Qwen2.5-7B-Instruct-AWQ --max-model-len 4096
# 或在线压 FP8(需要较新显卡):
vllm serve Qwen/Qwen2.5-7B-Instruct --quantization fp8

决策链：权重放不下 → AWQ/FP8；KV 放不下 → --kv-cache-dtype fp8；两者可叠加。

8.5结构化输出（Structured Output）：让模型只吐合法 JSON

问题：让模型输出 JSON，它时不时多句嘴或括号不配对，下游程序崩溃。

原理（vllm/v1/structured_output/）：把输出文法（JSON Schema）编译成状态机/自动机，每步解码前，把"不合语法"的 token 的 logits 强制置为 -inf——模型只能在合法 token 里选。v0.31 默认用 xgrammar 引擎，速度快。

用法（OpenAI 兼容）：

bash · curl
curl http://localhost:8000/v1/chat/completions -H "Content-Type: application/json" -d '{
  "model": "Qwen/Qwen2.5-0.5B-Instruct",
  "messages": [{"role":"user","content": "给一个学生打分: 张三 数学90 语文85"}],
  "response_format": {
    "type": "json_schema",
    "json_schema": {"name":"score", "schema":{
      "type":"object",
      "properties":{"name":{"type":"string"},"math":{"type":"number"},"chinese":{"type":"number"}},
      "required":["name","math","chinese"]}}}}'

代价：约束编译有一次性开销（自动缓存）；过度复杂的 schema 会拉高 TTFT。注意引导词（guided json）本质是"限制"，模型的语义质量仍取决于模型本身。

8.6LoRA 服务：一个基座带多个"角色"

原理：LoRA 是在原模型旁挂的低秩小矩阵（几十 MB），vLLM 可以在一个引擎里同时热插拔多个 LoRA 适配器，按请求路由。

bash
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --enable-lora --max-lora-rank 64 --max-loras 4 \
  --lora-modules customer-service=/path/lora-cs translator=/path/lora-tr

# 请求时指定用哪个适配器:
curl ... -d '{"model":"customer-service", "messages":[...]}'

适用：多业务共享一个基座省显存；LoRA 切换有轻微开销，超多适配器时留意。

实验命令观察点

第 01 章 · 大模型推理基础
CHAPTER 01

大模型推理基础：一次推理到底发生了什么

🔖 vLLM v0.31.0
本章目标：不写一行 vLLM 代码，先搞懂三件事 —— ① 大模型是怎么"一个字一个字"往外蹦的；② 显存都被谁吃掉了；③ 为什么需要 vLLM。这三件事是后面所有章节的地基，务必完全弄懂再往下走。

1.1大模型生成文字的真相：自回归循环

你平时用 ChatGPT，看到的是"一段一段回答"。但在 GPU 眼里，模型是这样工作的：

示意 · 自回归生成过程
输入: "天空为什么是"
第1步: 模型吃进整个输入 → 吐出 1 个词 "蓝"
第2步: 模型吃进 "天空为什么是蓝" → 吐出 1 个词 "色"
第3步: 模型吃进 "天空为什么是蓝色" → 吐出 "，"
...
直到吐出结束符 <eos> 或达到最大长度

关键认知：生成 N 个词 = 模型前向计算 N 次，每次只新产出 1 个 token。
这就是所谓的自回归（autoregressive）。

术语：token（词元）≈ 词的一部分。中文里大约 1 个汉字 ≈ 1~2 个 token，英文里约 0.75 个单词 = 1 个 token。模型所有操作的对象都是 token，不是"字"。

两个阶段：Prefill 与 Decode

阶段做什么计算特点
Prefill（预填充）处理整段输入 prompt，一次算完所有输入 token计算密集型（大量并行矩阵乘法），GPU 像赛车
Decode（解码）每步只算 1 个新 token访存密集型（要反复搬运整个模型的权重），GPU 像被限速

为什么 decode 慢？因为每生成 1 个 token，都要把几十亿参数全部从显存搬一遍到计算单元，而计算量只有一点点 —— 显存带宽成了瓶颈。这是后面理解"批量处理能摊薄成本"的伏笔：一个 batch 里 100 个请求一起 decode，权重只搬一次，每个请求分摊的搬运成本降为 1/100。

1.2KV Cache：空间换时间的必然选择

没有 KV Cache 会怎样？

Transformer 的注意力机制需要"拿当前 token 与所有历史 token 做运算"。如果每生成一个新 token 都重算全部历史 token 的中间结果，生成 1000 token 的回复，计算量会随长度平方爆炸 —— 完全不可行。

KV Cache 的思路

模型在处理历史 token 时，把每个 token 在每一层产生的两个中间向量—— K（Key）和 V（Value）—— 缓存起来，后续步骤直接查表复用：

示意 · KV Cache 更新步骤
生成第 t 个 token 时:
  1. 只计算第 t 个 token 的 Q/K/V（新算的只有这一个）
  2. K_t、V_t 追加进缓存
  3. 用 Q_t 与缓存里的 [K_1..K_t]、[V_1..V_t] 做注意力

代价是：这些缓存必须一直躺在显存里，直到这个请求结束。

算一算：KV Cache 到底多大？

公式（每个 token 的 KV 大小）：

$$ S_{kv} = \underbrace{2}_{K,V} \times L \times H_{kv} \times d_{head} \times \text{每元素字节数} $$

其中 $L$ 为层数，$H_{kv}$ 为 KV 头数，$d_{head}$ 为每头维度。

以 Qwen2.5-7B（FP16）为例：28 层、GQA 4 个 KV 头、每头 128 维、2 字节：

$$ 2 \times 28 \times 4 \times 128 \times 2 = 57{,}344 \text{ 字节} \approx 56 \text{ KB/token} $$

结论一览（FP16）：

模型每 token KV生成 1000 token4096 token 上下文
Qwen2.5-0.5B≈ 12 KB12 MB49 MB
Qwen2.5-7B≈ 56 KB56 MB224 MB
Llama-3-70B≈ 320 KB320 MB1.3 GB

动手验证：不用背，用这个一行脚本（把参数换成你的模型）：

kv_size.py
# kv_size.py —— 换任何模型，算出它的 KV Cache 开销
n_layers, n_kv_heads, head_dim, bytes_per = 28, 4, 128, 2   # Qwen2.5-7B fp16
kv_per_token = 2 * n_layers * n_kv_heads * head_dim * bytes_per
print(f"{kv_per_token/1024:.1f} KB/token, 4096 token 占 {kv_per_token*4096/1e9:.2f} GB")

看到 7B 模型一个 4096 长度的请求就要吃掉 224 MB 显存，你就能理解：

一个 80GB 显存的 A100，权重只占 140GB(FP16 70B)~ 的一半，剩下的显存全部是给 KV Cache 的"座位"。

vLLM 的核心使命：让这些座位利用率做到最高。

KV Cache 大小计算器拖动滑块，直观感受任意模型的 KV 显存开销（对应 1.2 节公式）

1.3vLLM 出现之前：三种"坐法"都在浪费座位

假设显存里有 40GB 专门留给 KV Cache。传统推理引擎（比如 HuggingFace Transformers 原生 generate）怎么安排这些空间？

方式一：按最大长度预留（Reservation 浪费）

示意 · 预留浪费
请求来了 → 按 max_len=4096 给它预留 224MB → 实际它只生成了 50 个 token
结果: 97% 的预留空间白白锁死，别的请求用不了

方式二：连续大块分配（碎片浪费）

每个请求的 KV 必须放在一整块连续显存里：

示意 · 外部碎片
显存: [请求A: 300MB][请求B: 500MB][请求A结束后空出300MB][请求C: 需要400MB ❌放不下!]
       ↑ 300MB 空闲碎片明明够 400MB 用的一部分，但"必须连续"导致谁都用不了

方式三：静态批处理（时间浪费）

凑一批请求（比如 8 个）→ 一起跑 → 最慢的那个结束才放下一批：

示意 · 静态批处理空转
第1批: [R1 ✓完成(3步)] [R2 ...还在跑(第25步)] [R3 ✓完成(4步)] ... R2 跑完才进下一批
       ↑ 7 个座位空转了 20+ 步，GPU 在干瞪眼

这三种浪费同时存在，GPU 的真实利用率往往不到 40%。

三种浪费 vs 分页传统引擎的"座位浪费率"直观对比（对应 1.3 节）

1.4vLLM 的答案

vLLM（UC Berkeley 团队，2023 年论文《Efficient Memory Management for LLM Serving with PagedAttention》）借鉴操作系统虚拟内存和分页的思想，逐个击破：

传统浪费vLLM 方案类比操作系统详见
按最大长度预留KV 按需分配小块（block），用多少分多少虚拟内存分页第04章
连续分配碎片每块 16 token，逻辑连续物理散落，免碎片页表第04章
空间不能共享相同前缀的请求共享 KV 块共享内存页 + 引用计数第04章
静态批处理空转每步（token 级）动态进出，即完成即让位CPU 时间片调度第05章

实测效果（官方论文，7B~13B 模型）：吞吐量比当时主流方案提升 2~4 倍，长请求、大并发下优势更大。

vLLM 的现状（截至本教程撰写）

  • 2026 年 10 月最新版 v0.31.0，V1 架构已完全成熟
  • 已成为业界事实标准：各大云厂商的模型服务、推理平台底层大多是 vLLM
  • 支持几乎所有主流开源模型 + 各种量化方案 + 多卡/多机
吞吐量对比vLLM 相对 HuggingFace 原生 generate 的吞吐提升（对应 1.4 节）

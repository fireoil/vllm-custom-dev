第 05 章 · 调度器与连续批处理
CHAPTER 05

调度器与连续批处理（GPU 不停转的秘密）

🔖 vLLM v0.31.0🔧 动手实验
本章目标：搞懂 vLLM 每一"步"（step）里调度器做的所有决定——收谁、切多长、放不放、抢谁的。学完你能读懂调度日志、并用 --max-num-seqs / --max-num-batched-tokens 等参数做定向调优。

5.1连续批处理：从"整桌结账"到"即来即走"

静态批处理（传统）像老式食堂：凑够 8 个人一桌，整桌吃完才清桌。

示意 · 静态批处理
一批请求: [R1要3步][R2要25步][R3要4步]...
实际过程: R1 第3步完成 → 座位空转 22 步; R3 第4步完成 → 继续空转...
GPU 每步 batch 变小 → 每步的有效算力占比不断下滑

连续批处理（Continuous Batching / In-flight batching，Orca 论文 2022 提出、vLLM 发扬光大）：调度器以"每生成一个 token 为一个节拍（step）"，每个节拍：

  1. 谁完成了？→ 立刻让出座位，吐出结果
  2. 有空位吗？→ 立刻接纳新请求（先做它的 prefill）
  3. 剩下所有人 → 一起 decode 一步

座位从不空转，吞吐量因此成倍提升（第 01 章埋的伏笔在这里兑现）。

静态批处理 vs 连续批处理动画对比：看座位何时空转、新请求何时进场

5.2调度器的一个节拍：schedule() 全流程

源码：vllm/v1/core/sched/scheduler.py 的 Scheduler.schedule()。它是 vLLM 最重要、也最值得读的一个函数。逻辑骨架（伪代码）：

vllm/v1/core/sched/scheduler.py（伪代码）
def schedule(self) -> SchedulerOutput:
    # ① 本步预算：最多处理多少 token、最多带多少请求
    token_budget = self.max_num_batched_tokens     # 默认 8192
    seq_budget   = self.max_num_seqs               # 默认 1024（V1 默认 1024，早期 256）

    # ② 优先"还债"：上步被抢占的请求要恢复（其 KV 需重新 prefill）
    # ③ 再续"旧客"：running 队列里的请求，每人预支 1 token 做 decode（开销固定）
    # ④ 然后接"新客"：从 waiting 队列弹请求做 prefill：
    #      - KVCacheManager.allocate_slots() 失败(块不够) → 停止接客
    #      - prompt 太长放不下预算 → chunked prefill 切片, 本步只算一部分
    # ⑤ 若连 decode 的 1 token/请求都放不下 → 抢占(preempt):
    #      挑最新/最小的请求, 释放它的 KV 块, 塞回 waiting 头部(RECOMPUTE 策略)
    # ⑥ 打包 SchedulerOutput: 每个请求的 block_table、采样参数、待 decode 列表...

三个关键机制展开：

① Chunked Prefill：把大请求的 prefill 切成"小口吃"

问题：一个 8000 token 的 prompt 一步算完，会把整步时间拖到几百毫秒，排在后面的所有 decode 请求的 ITL（逐 token 间隔）全部卡顿——流式用户体验骤降。

方案（V1 默认开启）：prefill 按预算切片，比如每步只吃 2048 token。副作用几乎没有（prefill 之间可以混入别人的 decode），收益是流式延迟大幅平滑。这也是 V1 架构相对 V0 的重大简化：调度器不再区分 prefill 批和 decode 批，统一混批。

② 抢占（Preemption）：块不够时牺牲谁？

当所有请求的 KV 块加起来超了（allocate_slots 返回 None）：vLLM 选择抢占而不是拒绝——把某个请求的 KV 全部释放、请求塞回队列最前，等下次轮到它时从上次断点重新 prefill（RECOMPUTE 策略）。被抢占者优先选"最晚进来的"（损失最小）。

为什么"重算"反而合理？因为 KV 块是稀缺资源：牺牲一个请求的已算成果，换回几块显存让 N 个请求继续出 token，净收益为正。这就是第 04 章实验 4-3 日志里 Preempted ... (RECOMPUTE) 的含义。

③ 两级队列与顺序

  • waiting（新请求 + 被抢占恢复的）按到达顺序（默认 FCFS，也支持优先级调度）
  • running（本步在跑的）

预算顺序：被抢占恢复 > running decode > waiting prefill——先保证已承诺的请求不被饿死。

5.3每步之后：token 怎么变成流式回复

节拍结束，EngineCore 把每请求的新增 token id 发回前端：

output_processor.py 调用链
output_processor.py (vllm/v1/engine/output_processor.py)
  → detokenizer.py: token id → 文字（增量分词还原，处理 UTF-8 截断）
  → 按 request_id 推进对应 asyncio.Queue
  → api_server 把它包装成 SSE 流发给客户端

对用户而言就是"打字机效果"；对 vLLM 而言，每一步都可能是某个请求的最后一个 token——它退场、座位释放、新请求进场，循环往复。

5.4调度相关参数速查（背下来，调优时用）

参数默认作用什么时候动它
--max-num-seqs1024同批最多请求数小显存/小模型调小（如 32~128），防碎批拖慢单步
--max-num-batched-tokens8192每步 token 预算追求低 ITL 可调小；追求吞吐可调大
--max-num-partial-prefills1同时允许几个"切了一半"的 prefill长 prompt 多时调大
--long-prefill-token-threshold0（不切）超过该长度才触发 chunked prefill混合长短请求时调优
--num-scheduler-steps1每次前向内部连跑几步（多步调度）一般不动
--scheduling-policyfcfsfcfs / priority有优先级业务需求时

V0 时代还有 --swap-space（CPU 交换 KV）与抢占 SWAP 策略；V1 以 RECOMPUTE 为主，并引入了 KV offload 等新机制（第 08 章）。看到旧教程讲 SWAP 策略要意识到版本差异。
